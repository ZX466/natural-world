## 3. live↔快照对拍现状（K1 实测缺口的当前状态）

### 3.1 缺口本身仍在

`gen-protocol --check` **只校「生成物 ↔ 快照」**，**不校「live ↔ 快照」** ⇒
「sim 加了路由但快照没注入」这类漂移**仍然不会自动报红**。K2 补了诊断路由，但**门禁缺口本身未补**。

### 3.2 现在的实际漂移（实测，`ext.install()` 后取线上 spec）

| 维度                   | 结果                                                                                                                                                                                                                                             | 性质                     |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------ |
| **paths 键集**         | live-only **0**、snapshot-only **0** ⇒ **路由面零漂移**（K2 补齐见效）                                                                                                                                                                           | ✅ 已闭合                |
| **schemas 键集**       | live-only：`HTTPValidationError`、`ValidationError`（FastAPI 自动校验模型，快照按体例不收）；snapshot-only：`WsEnvelope`（手工补的 WS 信封，live 无对应）                                                                                        | **系统性/设计性**        |
| **共同 schema 字段级** | 4 处不同：`AnchorMaterializationStatus`（**唯一差异＝`reason` 的 `"title":"Reason"`**，pydantic 自动标题，快照不带 title；结构/必填/封闭性完全一致）、`ProfileCreate`、`ProfileListItem`、`ProfileUpdate`（手写快照多 `description` 且键序不同） | **表述性**（无语义差异） |
| **共同 path 字段级**   | 9 处不同，差异字段**全落在 5 类**：`operationId`（FastAPI 自动名 vs camelCase，前端类型名由后者派生）、`summary`、`description`、`tags`、`parameters`（内联 vs `$ref` 归一）                                                                     | **表述性**               |

### 3.3 ⚠ 新发现：响应码缺口**双向**（pre-existing，非 M6 引入）

| 方向            | 路由                                                                                                  | 差异             | 性质                                                                                                                                                                                                                |
| --------------- | ----------------------------------------------------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| live 有、快照无 | `POST /api/anchors`                                                                                   | **`400`、`422`** | **真缺口**：ext 的 `_attach_problem_responses` 明确 `attach("/api/anchors","post",["400","422"])`，而快照只声明 `201` ⇒ 前端类型里**没有「世界未就绪」的 400**                                                      |
| live 有、快照无 | 其余 9 条路由                                                                                         | 仅 `422`         | 系统性（FastAPI 自动校验响应；快照按体例不收，可不落但**应登记**）                                                                                                                                                  |
| 快照有、live 无 | `GET /api/anchors/{anchor_id}`、`DELETE/PATCH /api/settings/profiles/{profile_id}`、`POST …/activate` | **`404`**        | **真缺口（反向）**：这些路由**确实抛 404**（`anchors.py:540` 抛 `anchor-not-found`；`settings.py:226/233/240` 抛 `profile-not-found`），快照也声明了，但 **ext 的 attach 清单漏了它们** ⇒ **live spec 缺 404 声明** |

**为什么重要**：前端类型面（`shared/protocol.ts`）来自**快照**，所以「快照缺 400」直接少一类错误分支；
而「live 缺 404」会让**按 live 生成的下游文档/客户端**与快照不一致。两条都该修，但**修哪一侧要显式决策**
（我建议：**快照与 ext 双向补齐**，各自一句 `attach` + 快照一行，属 minor 零版本位变更——
但这需要另立快照单，**不在本单所有权**）。
