## 0. 一句话 + 两问速览

**一句话**：`load_outcomes` 是死账本，而它背后的**执行出口 `drain_pending_loads` 在生产上根本没有调用方**
⇒ 读档请求只被**受理**（玩家已收到 `session_state` + `full_snapshot`），**分叉从不执行**，且失败无任何出站通道。

| 问                                | 答                                                                                                   | 依据 |
| --------------------------------- | ---------------------------------------------------------------------------------------------------- | ---- |
| 删还是接？                        | **推荐「接线案」的最小形**（先给 drain 一个生产调用点 + 失败落既有 `error` 帧），**不推荐直接删**    | §3   |
| 为什么 A9「死列不用」判例不适用？ | A9 治的是**DB 列**（写了没人读）；这里是**内存账本**且**已被测试读**，且它背后是一条**缺失的调用链** | §3.3 |

## 1. 事实链（逐跳实测，2026-10-03 main `2bd2bff`）

1. **受理（同步、不阻塞）**：`ws.py::_handle_load_anchor` → `_ANCHOR_LOAD_HOOK`
   = `main.py:113 _production_load_hook`（把 `(request_id, anchor_id)` 塞进 `pending_loads`，
   **返回 `True`**）⇒ `ws.py:882-888` **立刻**发出 `session_state`（分叉告知）+ `full_snapshot`。
   注释自己写着「失败由 driver 侧记 load_failed」（`main.py:117`）。
2. **执行（异步）**：`main.py:119 _drain_loads` 逐个 `popleft` → `orchestrate_load_anchor(...)`；
   成功/失败分别 `main.py:139/137` 追加 `load_outcomes`。
3. **出口注册**：`main.py:156-157` 把 `drain_pending_loads` 与 `load_outcomes` 挂到 `app.state`。
4. **⚠ 关键事实：生产无调用方**。全仓搜 `drain_pending_loads` 只有三处非测试命中
   ——定义（`main.py:119`）、docstring 提及（`main.py:114`）、注册（`main.py:156`）；
   **唯一的调用方是测试**（`sim/tests/test_m5_anchors_crud.py:286-291` 手动
   `getattr(app.state, "drain_pending_loads")` 后自己跑一轮）。
   ⇒ **driver 循环从不执行读档分叉**；`pending_loads` 只进不出。
5. **账本无生产消费**：`load_outcomes` 唯一读者是同一个测试（`:294` 断言 `outcomes[-1][0] == anchor_id`）。
6. **失败静默**：`_drain_loads` 的 `except Exception`（`main.py:133`）只
   `logger.warning("fork.load_failed", …)`；`AnchorMaterializationError`
   （`anchor_package.py:154`，五原因码固定集）在此被降级为日志——**到不了任何出站帧**
   （与 K14 核对单 §1.1 的结论一致，此处是它的**根因侧**：不是「错误码选错」，而是**没有消费者**）。

## 2. 影响面（玩家侧与运维侧各一条）

| 面     | 现状                                                                                                                                                                                       | 判据                                                       |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| 玩家   | 点「读档」→ 收到**成功形态**的告知帧 + 全量快照 → **世界线从未分叉**（回到的还是同一条线）；若真发生物化失败（`no_package`/`corpus_mismatch`/…）也**完全无声**                             | ①`pending_loads` 无生产消费（§1.4）；②失败只落日志（§1.6） |
| 运维   | 唯一线索是 `fork.load_failed` 日志行（带 `reason=str(exc)`，**工程词**）；`load_outcomes` 里的 `(anchor_id, ok)` 只在测试进程里存在                                                        | `main.py:133-139`                                          |
| 数据面 | 批次 E 的**只读诊断面已存在但无出口**：`anchor_package.py:485 MaterializationDiagnosis`（`ready/reason/snapshot_seq/steps`）——产品本可据此显示「该档不可回退」，却没有任何调用方把它送出去 | `anchor_package.py:485`                                    |

> **这不只是「死账本」**：`load_outcomes` 只是**症状**；**病根是执行链缺一个生产调用点**。
> 只删账本不修链，读档仍然静默无效——那会把唯一可观测面也一起删掉。

## 3. 两案 + 推荐

### 3.1 案 A：删除案（连测试断言一起清）

- 动作：删 `main.py:141/157` 的 `load_outcomes` 与 `app.state.load_outcomes`，
  删 `test_m5_anchors_crud.py:283-295` 的手动 drain + outcome 断言。
- 收益：去掉一个只服务测试的内存结构；不留「看起来像观测面其实没人读」的死代码。
- 代价：①**读档仍然静默无效**（病根未动）；②批次 E 物化诊断面彻底没有出口，
  M6-P0 想做「该档不可回退」的玩家提示时，要**从零**再搭一次观测链。

### 3.2 案 B：接线案（推荐，M6-P0 物化诊断面的序内活）

- 动作（**最小形**，按依赖顺序）：
  1. **给 `_drain_loads` 一个生产调用点**：在 driver 的 flush 后 `await` 窗口里执行
     （与 `K4 §3.4`「批量范式」同款：受理同步、执行异步、失败不回滚受理）；
  2. **失败落既有 `error` 帧**：`code` 沿用 **`load_failed`**（11 项闭合集**不扩**），
     `detail` 用**戏内第一人称口语**（禁把 `no_package`/`corpus_mismatch` 等工程词或量值写进玩家可见文本），
     `reason` 只进**日志字段**（`fork.load_failed` 已有该行，加 `reason=` 即可）；
  3. **`MaterializationDiagnosis` 的 `reason` → 玩家文案**做一层**戏内映射**（诊断面已存在，只缺映射表）。
- 收益：①读档从「静默无效」变成「有效或可读地失败」——**这才是 fail-closed 的完整形态**；
  ②批次 E 诊断面有了出口，M6-P0 的「该档不可回退」提示**不必从零搭链**；
  ③账本 `load_outcomes` 可以**降级为纯调试用途**（或随案 A 一并删——接线完成后它的价值只剩本地调试）。
- 代价：需要 driver 侧接线（**Claude 的写锁根治面**，见 §4）；要一条「诚实态」决策（§4-3）。

### 3.3 推荐：**案 B 的最小形**，且**接线完成后再按案 A 收尾**

- 判据一：**A9「死列不用」判例不适用于此处**。A9 治的是 DB 死列（`schema.md:901-903`
  的 `snapshot_seq`/`snapshot_tick`）——写了没人读 ⇒ 删；这里是**内存账本**，
  它对应的是一条**缺失的调用链**，删它＝把「唯一可观测面」连同症状一起抹掉。
- 判据二：**先接线再删**的顺序不可颠倒。若先删账本，接线时就少了一个「结果核对」的落点
  （测试要改成断言 `error` 帧或日志，反而更绕）。
- 判据三：**扩 WS 错误码不是这一步**。若要机器码级区分「物化包缺失（可重试）」vs
  「语料不匹配（数据坏了）」，那是 WS 词表 11→12，须同 CR + 前端消费分支——
  与 `anchors-api.md` §2.1 登记单的「归 kilo 单独立单」口径一致，**不在本单**。
- **不推荐的第三种**：把 `load_outcomes` 暴露成 HTTP 路由（玩家可读的失败清单）。
  那是**把内部失败面变成可枚举的对外机器码面**——与 A9 死列判例同款错位，
  且批次 E 诊断已经给了更精确的只读面（`MaterializationDiagnosis`），路由是绕远路。

## 4. 与 driver 写锁根治的接缝（Claude 施工面，本单不改）

| #   | 接缝点                 | 审计给出的约束                                                                                                                                                                                                                                                                                                                                                                    |
| --- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **调用点位置**         | 必须在 driver 的 `on_flush_async()` 之后的 `await` 窗口执行（`main.py:147-150` 已是该形态）。放在 flush **之前**会让读档分叉与 in-flight 批次竞态（`fork_from_anchor` 的 `preflush` 契约要求先冲干净）                                                                                                                                                                            |
| 2   | **写锁与背压**         | `_drain_loads` 逐个 `popleft` 是**无界**的：连续读档请求会把队列堆起来，而每个都要真分叉。写锁根治时应给**单帧执行上限**（例如每帧最多 N 个，超出的留到下一帧），否则一次批量读档会卡住 driver                                                                                                                                                                                    |
| 3   | **诚实态（需主树裁）** | 受理是**乐观**的：成功帧在分叉**之前**就发了。失败时那两帧收不回 ⇒ 玩家会先看到「读档成功」再看到失败（或什么都看不到，取决于是否接线）。三选一：(a) 受理帧改中性文案（「正在回溯…」）；(b) 成功帧延后到分叉成功后发（**契约面改动更大**：D-6 的「一帧双载」时序要重排）；(c) 接受现状＋至少给失败 `error` 帧。**审计倾向 (c)+`reason` 日志**（契约零改动），但这需要主树明确点头 |
| 4   | **异常不得外溢**       | `except Exception` 已是全域捕获（`main.py:133`）；接线后请**保持**——读档失败绝不能让 driver 主循环崩                                                                                                                                                                                                                                                                              |
| 5   | **观测字段**           | `fork.load_failed` 建议带 `anchor_id`/`request_id`/`reason`（前两者已有，`reason` 现在是 `str(exc)` 整串，建议换成 `AnchorMaterializationError.reason` 的**固定集码**，别把整串异常打进日志）                                                                                                                                                                                     |

## 5. 采纳接线案时的前置钉（零生产码，可先落）

若主树采纳案 B，以下三条**测试钉**可在施工前先立（届时零回归）：

1. **执行面**：起 WS `load_anchor` 后**不手动跑 drain**，断言分支数真的 +1（当前必红——这
   就是病根的可执行形态；接线后自动转绿，**不要 skip-lock**，它红就红得对）；
2. **失败面**：构造 `AnchorMaterializationError("no_package")`（用既有 monkeypatch 缝注入），
   断言玩家收到 `error` 帧且 `code == "load_failed"`、`detail` **零工程词**
   （`assert "no_package" not in detail`）；
3. **不扩码面**：断言 WS 错误码词表**仍是 11 项**（本条今天即绿，防接线时顺手扩码）。
