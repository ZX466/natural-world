# 性能热点预判与对策（docs/perf/hotspots.md）

> 依据：`DESIGN.md` §4/§7/§9/§10/§12/§13（v2.1）。本文在 M0 前预判热点，每条给「现状 → 成本 → 至少一个可选方案 → 取舍」，具体取舍由 Claude（架构）裁定，本域只在性能维度给证据。
> 与 `budget.md` 配套：每条热点标注对应预算项。

## H-1 感知传播：射线遮挡 + 1/r 衰减（对应预算 §2.5）

**现状**：视觉 = 射线遮挡完全阻断；听觉 = ∝1/r 穿墙衰减不阻断；嗅觉(M2) = ∝1/r² 风向主导（§7）。50 NPC + 主角，M1 起视觉/听觉每 tick 对可达对子做传播。

**成本**：最坏 50×49 = 2450 对子/tick；若每条视觉都打射线（Bresenham/DDA 逐 tile），按 242 tile 地图最坏 ~50×50×平均 ray 步数，远超 §2.5 预算 3.00ms 上限。听觉 1/r 若逐对计算也是 O(N²)。

**可选方案（择一或组合）**：
1. **空间分区 + 候选剪枝**：uniform grid（tile 块）预筛可视/可听候选，射线只在候选对打；听觉按距离 r 阈值先 cull，再衰减。→ 最稳，O(N·k)。
2. **增量可见集（VPT 风格）**：维护每个感知者的可见/可听集合，只当「位置/光照/遮挡物」变化或新事件落点变化时差分重算。→ tick 均摊最少，但状态一致性维护复杂度高，与确定性（C5）叠加后入侵面大。
3. **节拍降采样**：视觉传播每 2 tick、听觉每 tick；光照/雾修正低频 pass（触发式或每 N tick）。→ 收益确定、实现最简单，但与 §10「1 tick = 1 秒世界」的观感有细微时差（多数场景不可感知）。

**取舍**：M0 先用 1（分区 + 剪枝）+ 3（降采样）打底，成本可测；1 坏了再上 2。预算上限 3.00ms 内优先保证可见/可听集正确（这是 C2 信息边界的事实防线），不得为性能丢正确性。

**M2 嗅觉延伸（对应预算 §2.9）**：∝1/r² 且风向主导、需持续源，与视觉/听觉同构但不可用同一套分区剪枝——逐时变风场下每对子都要重算风向投影，逐对成本比听觉还高（M2-P1 实测逐对哨兵 ~4.6ms，见 `test_bench_smell.py`）。对策：改 Eulerian 网格增量扩散（源发射 → 全图平流 → 衰减），场隐式承载 1/r²，接收端 O(1) 采样；实测 ~0.01ms/tick。详见 budget §2.9。

## H-2 L0 千人级统计模拟（对应预算 §2 L0 独立通道）

**现状**：L0 = 地图外周边区域的统计模拟，千人级，每分钟推进（§13），L1 满分是战力，L0 是背景噪声。按 §4 用 numpy 批量推进。

**成本**：千人级 × 分钟级 = 数据量小，真正的坑是**逐对象 Python 热循环**（千人朝它跑就起飞）。

**可选方案**：
1. **结构化数组 + 向量化**：一维 numpy 数组承载千人状态（需求衰减、位置统计、供需量），一次 `arr = arr * decay + inflow` 完成推进；杜绝 for 循环。
2. **碎片重算**：L0 只重算最近变化的子集（diff 驱动），静态多数直接复用上一分钟结果。
3. **降频**：弱活动时段（深夜）L0 推进降为每 2 分钟，晨间恢复。

**取舍**：方案 1 是实现下限（不做就是热点），2/3 是后续优化。内存：千人 × 单条 ~64B 字段 ≈ 每字段不到 1MB 量级，无内存压力（批量内存，勿存为对象）。

## H-3 SQLite 事件日志 append-only（对应预算 §2.3/§2.6）

**现状**：事件溯源是唯一写路径（C4），世界档 append-only（C6）；快照每 1000 tick 一次，单份 ≤5MB gzip，同分支留最近 8 份热 + 每日首份，abandoned 分支冷归档（§12 v2.1）；主库稳态 <2GB。技术栈 SQLAlchemy 2.0 async + aiosqlite（§4）。

**成本**：
- 写入：稳态 ~20 事件/tick = 1200/秒。逐事件 commit 会死（fsync 上限 ~几百/秒）；批量 commit 是唯一出路。
- 索引：事件日志 append-only，主查询是「按 (branch_id, seq) 重放」和「按 seq > anchor 续读」——索引设计不当会让重放变 O(N log N) 甚至全表扫描。
- 快照体积：5MB × 86 份/游戏日 ≈ 430MB/日，若不做治理主库爆 <2GB 上限。

**可选方案（明确推荐组合）**：
1. **批量写**：事件先入内存队列，每 tick 或每几十 ms 一次批量 INSERT（SQLite 单事务多行），WAL 模式；fsync 频率按每 batch 一次（`synchronous=NORMAL` 起步，验证崩溃一致性后再调）。
2. **最小索引**：只保留 `(branch_id, seq)` 唯一索引（重放键）+ `seq` 自增主键；不为主库加冗余业务索引（冷归档后不再查询的段无索引负担）。追加写天然有序，避免随机页写。
3. **快照治理落库**：热快照保留 8 份、abandoned 整分支 gzip 移出主库为独立 SQLite；主库超过阈值把「快照点以前」的事件段整段移冷——治理策略写进 storage 层，而不是运维手工清。
4. （备选）重放预热缓存：读档时把最近快照 + 尾部事件段载入内存，重放毫秒级（§12 已要求）。

**取舍**：1+2 是 M0 必须落地（写路径是 C4 唯一写口）；3 是 M2 前落地。同步级别与确定性回放（T2）正交：种子确定的是内存态，落盘只影响崩溃恢复，两者分开建模。

## H-4 WS 广播频率（对应预算 §2.7）

**现状**：FastAPI + uvicorn WebSocket 网关（§4），Phaser 只画 canvas 内世界，React 只画 canvas 外 UI。每 tick 世界都在变，但表现层不需要每 tick 全量推送。

**成本**：每 tick 全量序列化 50 NPC + 地图 + patch → 数据量爆炸且客户端 60fps 也消费不过来；逐事件逐 tick 单独发又产生 1200 条/秒的包风暴。

**可选方案**：
1. **增量 patch + 帧合并**：每 tick 只发 dirty 增量（移动/状态变化的实体），按 1/15s 批次（~5–10Hz）聚合下发；客户端在帧内插值。
2. **分区订阅**：客户端按视口订阅区块，只推可视区附近实体；远区低频。→ 与缓存机制/寻路 chunk（§14）天然亲和。
3. **快照 + 增量双通道**：视觉基础帧低频全量，过程增量高频。

**取舍**：方案 1 是必须（否则带宽/CPU 双爆）；2 是 M1+ 优化。**关键约束**：推送的数据只可能来自戏外表现层通道，任何字段不得回流进 Agent prompt 或世界事件日志（C3 推论），即 WS 包与感知流是两条完全隔离的通道——性能优化不能把两条通道并线。

## H-5 超速倍率 4x/16x（对应 budget §4）

**现状**：1x=60 tick/s 时 16.6ms/tick；4x=4.16ms、16x=1.04ms（§10）。逐 tick 全速跑 = 追不上，CPU 100%。

**方案**：L1/感知按倍率降采样（1x 全速，4x 每 4 tick 推进 L1，16x 合并语义 tick，UI 独立出帧）。确定性不变（同一 seed → 同一世界结果），只变节拍粒度。
**取舍**：快进 = 低保真节拍是**明示承诺**（文档宣告），不允许悄悄降质；UI 帧率靠 Phaser 独立时钟，不绑架模拟节拍。

## H-6 LLM 异步延迟与大世界节奏（信息性热点，非 tick 内）

**现状**：LLM 思考时世界不暂停（异步 + 预取，§10）；L2 个位数 NPC 按需触发；断线降级 L1（§3）。
**成本表征**：不在 tick 预算内；用 §15 量纲：单决策 1.2–2k tok、一游戏日 40–60 次决策 ≈ 60–120k tok/日、决策延迟 P95<8s。
**对策（性能侧）**：单决策越 8s 会吃掉战斗交换单元余量（v2.1 战斗慢镜专门吸收 8s 尾巴）→ 度量 LLM latency + tokens 并把超时告警独立于 tick 告警；模型 Profile 单 profile、手动切换、无容灾（§15），不做自动重试风暴。
