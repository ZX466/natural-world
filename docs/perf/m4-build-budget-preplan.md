## 2. 坍塌级联成本模型（实测）
### 2.1 口径与图形态
- 承重图：N 节点、每节点 1..fanin 个父（有向无环，父建成更早 → 无环天然成立），
  反向邻接 = 父 → 直接依赖者（子）。随机 seed=7，逐层 `sort()` 保证稳定序
  （对齐 M4-D1 §5.1「按 `(structure_id, tile, kind)` 稳定排序遍历」）。
- 最坏口径：从根 0 出发的**全图级联**（N 节点全部坍塌）。对照：从叶出发只坍塌 1 个
  （实测 0.0004ms）——所以真实风险不是「每次坍塌」而是「最坏重灾」。

### 2.2 施工推进：每 tick 全扫（在建点 N）
| 在建点 N | 全扫 python（逐对象 ≤+β） | 全扫 numpy（向量化） | due 堆建（一次性） |
|---|---|---|---|
| 100 | 0.003ms | 0.001ms | 0.007ms |
| 1,000 | 0.030ms | 0.001ms | 0.055ms |
| 10,000 | 0.29ms | 0.004ms | 0.72ms |
**线性（~0.03µs/点 python、~0.0004µs/点 numpy）**。结论：**稳态施工推进本身不是风险**——
即使 1 万在建点全扫 python 也只用 0.29ms（1.8% tick）。瓶颈在「推进是否顺手产事件」（§3）。

### 2.3 坍塌：图物化 + BFS（图遍历）vs BFS + 逐对象派生事件
「图物化」= 按 M4-D1 §5.1 从 `structures` 投影行（`supported_by` = TEXT JSON 数组，
schema §9）建 `dependents: support_id → sorted[dependent_id]`（含 `json.loads`）；
**事件驱动重建（只在拓扑变更时）**，不是每 tick。

| N | 图物化（含 json.loads） | BFS 本体 | 逐对象派生事件 | tick 内合计 | 占 16.6ms |
|---|---|---|---|---|---|
| 100 | 0.10ms | **0.010ms** | 0.37ms | **0.38ms** | 2% |
| 1,000 | 1.11ms | **0.099ms** | 4.05ms | **4.15ms** | 25% |
| 10,000 | 11.17ms | **1.27ms** | 49.7ms | **51.0ms** | **307%** |

fanin 敏感度（N=10000，全级联，独立进程）：fanin=1 → 1.09ms；2 → 1.35ms；4 → 1.40ms；
8 → 2.01ms（边数 9999 / 15069 / 24945 / 44624）。**BFS 对 fanin 不敏感**（~0.04µs/边）。
图物化解耦度：纯邻接物化（无 json 解析）0.016/0.22/2.83ms（100/1k/10k）→
**json.loads 占物化成本 ~74-96%**；若投影层直接缓存解析后邻接可省。

**核心发现（本单最重要一条）**：**BFS 本体便宜到可忽略**（1 万节点 1.3ms = 8% tick），
**逐对象派生事件才是 binding 约束**——每个受影响对象要构造一条事件（~4µs）+ apply（~12-14µs），
1 万对象 = 51ms = **307% tick**。且坍塌是**一次性突发**（不是稳态摊销），无法靠每 tick 均摊。
→ 结论：坍塌必须**按帧摊还（cascade 分片）或对级联规模设硬上限**，
D1 M4-D1 §5.1「每个实际受影响对象产生一次 collapse 事件」在 1 万级会破线（§3.4）。

### 2.4 事件单价（M4 一切热路径的共同乘数）
| 操作 | 单价 | 来源 |
|---|---|---|
| `matter_event(...)` 构造（pydantic 校验 + frozen model） | **~4.0µs/事件** | 实测 N=50/500 = 0.189/1.93ms，线性 |
| `tile_changed_event(...)` 构造 | **~2.8µs/事件** | 实测 N=50/500 = 0.138/1.37ms |
| `move_event(...)` 构造 | ~4.5-5.0µs/事件 | 实测 N=50/500 = 0.224/2.48ms |
| **`EventBus.apply(move)`（唯一写路径 C4，含 handler 派发）** | **~12.1-14.3µs/事件** | 实测 50 事件批 0.604ms → 12.1µs；500 事件批 7.17ms → 14.3µs |
| **事件全链（构造 + apply）** | **~17µs/事件** | 上两行之和（=`budget.md §2.3`「~20µs/事件」量级，互为佐证） |
**「事件数」是 M4 的一阶变量**：任何「每 tick 每对象产一条事件」的设计，
S 个对象 = S × 17µs/tick。50 对象 = 0.85ms/tick（超 M4 额度四成），
100 对象 = 1.70ms/tick（贴上限表余量 2.10ms）——**这是施工推进语义的硬约束**（§3）。

## 3. 施工推进语义的 perf 侧建议（与 opencode M4-D1 交叉）
### 3.1 事件量对比（一日 = 86,400 tick；事件全链 17µs）
| 方案 | 事件/tick（S=50 在建点） | ms/tick | 事件/日（S=50） | 判定 |
|---|---|---|---|---|
| A 每 tick 一条 delta（S=50） | 50 | **0.85** | 4,320,000 | ❌ 超 M4 额度 40%；S=100 时 1.70ms 贴线 |
| C 阶段 checkpoint K=24/日 | 0.014 | **0.00025** | 1,200 | ✅ |
| C 阶段 checkpoint K=144/日（约 10 分钟游戏时一存） | 0.083 | **0.0015** | 7,200 | ✅ |
| C 阶段 checkpoint K=1440/日（约 1 分钟游戏时一存） | 0.833 | **0.014** | 72,000 | ✅ |
| B 只终态（每木棚 1 次完成事件） | ~0 | ~0 | 50 | ❌ 可恢复性丢失（非 perf 问题） |
**→ 性能侧明确支持 M4-D1 §4「STARTED + 有界 checkpoint + 终态」**：
checkpoint 事件量比方案 A 低 **3–5 个数量级**，perf 侧零压力。
checkpoint cadence 的选择**完全不受 perf 约束**（K=1440 也只 0.014ms/tick），
应由数据面按「重放尾部重算上限」定（D1 §4.3 待裁点），性能侧只标注：
**cadence 越稀，尾部确定性重算的 tick 数越多**——若选无 checkpoint 纯尾部重算，
重算窗口不得把 tick 拖过 16.6ms（建议单次重算上限 = 1 个 tick 预算 16.6ms，
与 D1 §4.3「尾部重算上限」待裁点配对）。

### 3.2 推进本体（BFS 之外的计算）
M4-D1 §4.2 的「tick 间由确定性纯函数推进」：实测**不是风险**（§2.2：1 万在建点全扫
0.29ms python）。建议：
- 推进用**同构数组 + `np.subtract/clip` 向量化**（对齐 budget §2.4 L1 同款），
  1 万点 0.004ms；
- 若必须逐对象 python（含 quality/integrity/rule 分支），1 万点仍只要 0.29ms，
  **无需 due 堆**（堆建一次性 0.72ms 反而比全扫贵，仅当在建点 > 数万才划算）。
→ **反对过早引入 due 时间轮**（复杂度 > 收益）；先全扫，实测破线再上（§4 触发器）。

### 3.3 材料守恒事件（MATERIAL_MOVED）
M4-D1 §6.2 的 `MATERIAL_MOVED` 是**每笔转移一条事件**。建设性建议（性能侧）：
- 单次建造会话的材料转移次数 = O(1)（不是每 tick）；50 并发建造 × 每次 1-3 条
  = 50-150 事件/tick 的**突发上界**，摊平后 ≪ 0.85ms/tick；
- 但**批量交付**（如一次性扣 50 份材料）应**一条 `MATERIAL_MOVED` 带 quantity**，
  不要拆成 50 条（D1 §6.2 已给 `quantity>0` 字段，性能侧确认该设计正确）；
- 幂等键（D1 §6.3）不引入额外 tick 成本（`transfer_id` 查表 O(1)）。

### 3.4 交叉点汇总（给 M4-D1 的输入）
| D1 提案点 | 性能侧实测输入 | 判定 |
|---|---|---|

| §4.1/§4.3 选「checkpoint + 终态」 | K=1440/日仅 0.014ms/tick | ✅ perf 零约束，cadence 由重放口径定 |

## 4. 红线草案（M4 真实现后实测定标；本单只给框架）
### 4.1 建议新增行（thresholds.py 追加，既有行不动；命名随实现落地确认）
| 项 | 草案值 | 依据 | 口径 |
|---|---|---|---|
| 施工推进单 tick（全扫式） | ≤ **0.50ms** | 实测 1 万在建点 python 0.29ms + 1.7x 慢机余量；破限先查是否退化为「每 tick 每对象产事件」 | `test_bench_build_progress`（暖态中位，warmup_rounds=1） |
| 坍塌单帧（BFS + 事件发射，含摊还） | ≤ **2.00ms** | 实测 100 节点端到端 0.38ms（含事件）+ 图物化 0.10ms；1000 节点 4.15ms > 2.0 → **红线同时是「必要摊还」的强制点** | `test_bench_collapse_cascade` |
| 坍塌级联规模上限 | ≤ **100 节点/帧**（草案） | 1000 节点端到端 4.15ms 破 2.0ms；100 节点 0.38ms 在余量内。实现可选：分帧 pop / 规模截断 + 剩余入队 | 契约测试（非 bench） |
### 4.2 不新增行（并入既有红线）
| 项 | 并入行 | 理由 |
|---|---|---|
| 施工/坍塌事件 apply | `APPLY_P99_LIMIT_MS=0.04` + `test_apply_50_events_batch`（2.0ms/50） | 事件 apply 是同一唯一写路径，无新机制；只需确保 M4 事件种类注册进总线后重新跑既有 apply bench |
| `MATERIAL_MOVED` 材料事件 | 同上 | 同上（MatterPayload 类事件） |
| 坍塌触发的 chunk 失效 | `CHUNK_INVALIDATION_TICK_LIMIT_MS=2.0` | 走既有 `Pathfinder.observe_events`（M3-P3），**坍塌批量标脏会放大「脏 chunk 数」**：§2.3 的实测成本模型（缓存条数 × 脏 chunk 数）在此复用 |
### 4.3 与 M4-D1 的接口（红线落地时对齐）
- D1 §5.1 的「按稳定序遍历 + 每对象一条事件」在 bench 里要**分别测 BFS、事件发射、端到端**三段，
  否则破线时无法判定是图遍历退化还是事件数超标（本单 §2.3 已给三段拆分基线）。
- D1 §9 待裁点 4「rubble 删除/tombstone」影响坍塌后的图规模 → 图规模变化要复跑 §2.3 三档。
- 红线定标前**不得**把草案值写进 thresholds.py 硬断言（本单是预研，非实现）。

## 5. 观察项（不设红线，留预审核）
- **坍塌事件的并发放大**：若同一 tick 有多次独立坍塌（火灾 M5 蔓延、多点破坏），
  每个级联各 0.38ms（100 节点）→ 3 次并发即 1.14ms。建议实现层**全局每帧事件预算**
  （类似 `budget.md §2.3` 事件 p99 50 条口径），而非每级联独立预算。
- **`structures` 物化频率**：M4-D1 §5.1「一次批量物化」如果是**每 tick**重建，
  10k 节点 11.17ms/tick = **67% 预算**（140k 节点即破线）。建议：
  **只在拓扑变更时重建**（事件驱动脏标记，与 D1 §5.3 图不变量 5 同节拍）；
  另 `json.loads` 占物化 74-96% —— 投影层可缓存解析后邻接（性能侧建议，非硬要求）。
- **chunk 失效与坍塌叠加**：坍塌 100 节点若各占不同 chunk，会一次性标脏大量 chunk →
  `PathCache.invalidate` 成本 = 缓存条数 × 脏 chunk 数（M3-P3 §5.2 实测）。
  48×48=9 chunk、4096 缓存打满时 1.18ms；M4 若地图扩大需按 M3-P3 档位重算。

  （与 L1/感知同款），M4 落地时要显式声明建造推进的降采样节拍。
