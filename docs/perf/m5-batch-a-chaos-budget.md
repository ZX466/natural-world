## 1. inject 摊摊（真随机注入侧账）

### 1.1 被测路径与频率
`EntropyMixer.mix(stream, tick)`（`sim/core/entropy.py`）= `os.urandom(16)` + `rng.reseed`（sha256）+ `entropy_event` 构造；调用方再 `EventBus.apply` + `flush_rows` 派生 `entropy_log` 行（与事件同事务落库）。

- **每日天气注入频率**（接线已定）：`daily_reseed_due(tick) = tick % TICKS_PER_GAME_DAY == 0`
  （`sim/world/weather.py:133`）⇒ **整 1 次/游戏日 = 1/86,400 tick**。这是 EntropyMixer 的首个生产调用方。
- **其余注入点**：DESIGN §11 事件驱动，opencode 预研 **20–150 条/游戏日**——非 per-tick。
- **每游戏日** = 86,400 tick（`sim/core/calendar.py::TICKS_PER_GAME_DAY`）。

### 1.2 实测单次成本
| 调用 | 中位 |
|---|---|
| `EntropyMixer.mix()` | **6.6µs** |
| `rng.reseed()` | 2.9µs |
| `entropy_event` 构造 + `EventBus.apply`（内存队列） | ~2µs（并入事件批） |
| `flush_rows` + SQLite 落盘 | 随事件批**摊销**（M5-P1：`SqlEventStore.append` 78.7µs/事件，按帧批写，非每 tick） |

### 1.3 摊摊结论
```
1 次/日: 6.6µs / 86,400 tick = 0.00008 µs/tick
150 次/日: 6.6µs × 150 / 86,400 = 0.011 µs/tick = 0.000011 ms/tick
即使计入事件/熵行落库（每 tick 事件批 ~20 条，注入只占其中少数），合计仍 ≪ 0.001 ms/tick
```
**结论：inject 本身对每 tick 预算无实质影响，无需红线。**

- **对照 M2 风场口径**（`m2-p4-budget-preplan.md` §1.2）：风冷键一次 `_wind_for_tick` =
  **0.018ms**（档内缓存命中均摊 ≈0）。inject 重播种（6.6µs）**比风场派生还轻**，且频率更低
  （1 次/游戏日 vs 风场每档变）⇒ 沿 M2 结论：inject 摊到每 tick **噪声级，不设独立红线**。
- inject 的真正「代价」是**重播种后下游每个 `chaotic()` 抽签值整体切换**（语义影响，非额外成本——
  下次 `chaotic()` 仍按新材料 9.3µs 算出新值，不增加调用次数）。

## 2. 消费点：寻路扰动两笔账 + 情绪回落

> 「两笔账」＝寻路扰动的**抽样本身**与**扰动触发重算**（任务卡明示）；情绪回落单独按每 tick 摊估。

### 2.1 单次抽签成本拆解（为什么是 9.3µs）
`chaotic()`/`chaotic_at()` 是**纯函数**（每次由流材料指纹重建独立 Generator，无进度、无调用序依赖）——这正是 C5「任意 tick 可独立重算」的代价。

| 组成 | 中位 | 占比 |
|---|---|---|
| `np.random.Generator(np.random.PCG64(seed))` + `gen.random()` | **6.8µs** | ~73% |
| `hashlib.sha256(material)` | 0.6µs | ~6% |
| `rng._material(stream)` | 0.7µs | ~8% |
| 调用/封装开销 | ~1.2µs | 余 |
| **合计 `chaotic()` / `chaotic_at()`** | **~9.3µs** | 100% |

**对照**：缓存 `gen.random()`（`RngRegistry.generator()` 复用 Generator）= **0.30µs**。
⇒ 纯函数重建是 **31x** 于缓存路径。这是「确定性 ≠ 预定」在抽签热路径的**结构性成本**，不是实现回归。

### 2.2 账一：寻路扰动（两笔账）
`Pathfinder.find()` 命中时抽 `chaotic()` 扰动路线（DESIGN §11「走路寻路」）。扰动要**明确写在哪个面**，
决定它到底动没动 `PathCache`（`(start, goal) → path`，见 `pathfinding.py`）——这是两笔账的分水岭。

| 账 | 触发 | 单次成本（实测本机） | 说明 |
|---|---|---|---|
| **账一-a 抽样本身** | 每次扰动抽一次 `chaotic()` | **9.3µs** | 纯函数重建（§2.1），与寻路本身无关 |
| **账一-b 扰动触发重算** | 扰动**写进缓存键 / 命中后改路** ⇒ 缓存失效 → 冷 A* 重算 | **494–647µs**（64×64，soak/感知同口径）**/ 366–439µs**（48×48 寻路 bench 图） | **~53–70x 账一-a**，两笔账里的真大头；随图幅继续增长（128×128 ~0.9–1.3ms） |

- **若扰动只作用于 find() 输出**（后处理：加小偏移/微折，不改缓存键）：`find()` 返回后调 `chaotic()`
  ⇒ 走**账一-a**（9.3µs），缓存仍命中旧路，**不触账一-b**。这是**推荐接法**。
- **若扰动进缓存键 / 走 A* 内部**（启发式/tie-break 被混沌改变 ⇒ 同 (start, goal) 出不同路）：缓存无法复用
  ⇒ 每寻路一次**冷重算**（494–647µs @64×64）。1 次/tick 即 ~0.5–0.65ms（≈5–6.5x RNG/熵行上限）；**反模式**。
- **寻路频率**：事件驱动（move/漫步 + 玩家 impulse），非每 tick；50 NPC 只有**实际移动者**才寻路。

| P（扰动寻路/tick） | 账一-a（9.3µs×P） | 若走账一-b（64×64 取 494–647µs×P） |
|---|---|---|
| 5 | 0.047ms | **2.5–3.2ms** |
| 10 | 0.093ms | **4.9–6.5ms** |
| 50（全员每 tick，反模式） | 0.465ms | **24.7–32.4ms（> 整 tick 预算 16.6ms）** |

**结论**：寻路扰动**必须走账一-a**（扰动只作用输出，不碰缓存键）——否则每寻路一次都冷 A* 重算，
P=5 即 2.5–3.2ms/tick（≈15–19% 整 tick 预算，并挤占 L1 6.0ms 行余量），P=50 直接顶穿整 tick 预算。**这是本单最重要的红线约束**。

### 2.3 账二：情绪回落
- **消费形态**：NPC 情绪（PAD）回落时抽一次 `chaotic_at()`（DESIGN §11「情绪回落」）。情绪是**慢变量**，回落是**区间采样**（非每 tick）。
- **每 tick 摊摊**（50 NPC × 区间 N tick）：
  | 区间 N | 每 tick 成本 |
  |---|---|
  | 60 tick（1 游戏分） | 50×9.3/60 = **0.0078ms** |
  | 600 tick（10 游戏分） | 0.00078ms |
  | 1（每 tick 每 NPC，反模式） | **0.465ms** |

**结论**：情绪回落若按区间（N≥60）摊估，**远低于**混沌余量（0.008ms ≪ 0.055ms）；但若实现里**每 tick 每 NPC 都抽一次**（把慢变量做成热循环），即达 **0.465ms/tick**，是 RNG/熵上限 0.10ms 的 **4.65x** ⇒ 必须避免（N 至少 ≥60，理想 ≥600）。

### 2.4 消费点合并（寻路扰动 + 情绪回落 vs RNG/熵行余量）
混沌抽签是 numpy 工作，与 L1 既有 RNG draws 同属 budget §1「RNG / 熵」行。该行**上限 0.10ms**，
其中 L1 常规 RNG（50 NPC × 4 draws = 200，**实测 0.045ms**，本机）占用大半 ⇒ **混沌只有 ~0.055ms 余量 ≈ 5–6 次/tick**。
（注：这是**抽签**（账一-a/情绪）的余量；**账一-b 的冷 A* 重算不属 RNG/熵行**，走寻路/事件 apply 面。）

| 场景 | 寻路扰动-a（抽签） | 情绪回落 | RNG(0.045) + 抽签 | vs 0.10ms 上限 |
|---|---|---|---|---|
| 推荐（事件驱动 + 区间） | 0.037（≈4 次） | 0.008 | **0.090ms** | ✓ |
| 合规贴线 | 0.046（≈5 次） | 0.008 | 0.099ms | ✓（贴线） |
| 反模式（每 tick 每 NPC） | 0.465 | 0.465 | **0.975ms = 9.8x** | ✗✗ |

> ⚠ 若寻路扰动走**账一-b**（冷 A* 重算），每寻路一次 ~500–650µs（64×64；48×48 ~370–440µs，128×128 ~1ms），**另计**——P=1 即 0.49–0.65ms，
> P=5 即 2.5–3.2ms/tick，不在上表 RNG/熵行内，直接占用事件 apply / L1 行量的余量（L1 上限 6.0ms，P≈10 即顶穿）。
> **结论：账一-b 必须禁，扰动只作用于 find() 输出（账一-a）。**

## 3. 红线建议

### 3.0 最紧要红线（语义约束，非阈值）：**禁扰动走缓存失效/重算**
- **红线**：寻路扰动只能作用于 `Pathfinder.find()` 的输出（后处理加小偏移/微折），**不得**把
  混沌值写进缓存键或喂进 A* 内部（启发式/tie-break）——否则同 (start, goal) 出不同路 ⇒
  缓存永不可复用 ⇒ 每寻路一次冷 A* 重算（494–647µs @64×64，§2.2 账一-b）。
- **为什么不是个数字阈值**：这不是性能实测越线，而是**接法选错就结构性爆预算**——P=1 即 0.49–0.65ms/tick（≈5–6.5x RNG/熵行），
  P=5 即 ~2ms/tick（≈12% 整 tick 预算，且挤占 L1 6.0ms 行的余量）。一旦禁死走错路，抽签本身（账一-a 9.3µs）根本不构成风险。
- **同时守住 T2/确定性**：若扰动走输出后处理，需保证「同 (材料, tick) → 同扰动」，否则回放逐位一致破（C5）。

### 3.0b P6 纪律：先探针后定标
`CHAOS_TICK_LIMIT_MS=0.05` 为**提案值**，**不直接进 thresholds.py**（本单零代码）。P6 教训：
绝对阈值在**降频机必假红**。落地前须在定标机（`throttle_probe.py` 比值 ~1.0）暖态中位实测定标，
未定标前该红线只 **advisory**；定标机无降频后才转硬断言。

### 3.1 建议：新增 `CHAOS_TICK_LIMIT_MS`，并入 RNG/熵行
```
# --- M5-P9：批次 A 混沌抽签每 tick 红线（提案待裁；施工后断言）---
# 依据 docs/perf/m5-batch-a-chaos-budget.md §2/§3 + budget.md §1/§2.2 RNG/熵 行。
# 混沌 = 确定性抽签纯函数（chaotic/chaotic_at ≈9.3µs/次，缓存 gen.random() 的 31x）。
# 红线卡「每 tick 混沌抽签聚合成本」，与 L1 常规 RNG 同属 RNG/熵行；
#   RNG(200 draws 实测 0.045ms) + 混沌 ≤ RNG_TICK_LIMIT_MS(0.10ms) ⇒ 混沌余量 ≈ 0.055ms ≈ 5–6 次/tick。
# 定标机暖态中位（warmup_rounds=1 + median）。破限先查消费点是否落入「每 tick 每 NPC」热循环，
# 改区间抽样/事件驱动，不得放宽红线。
CHAOS_TICK_LIMIT_MS = 0.05
```
- **为什么 0.05**：`0.10（RNG/熵上限）− 0.045（L1 常规 RNG 实测 200 draws，本机）≈ 0.055ms`，取整 0.05 ⇒ 混沌仅容 **~5 次/tick**。
  这是把混沌**并入既有行**而非另起炉灶的自然结论（budget §2.2 含 50 NPC × 4 draws 口径）。
- **语义**：红线只管「每 tick 混沌**抽签**总成本」，**不逐函数断言**（`chaotic` 的单次耗时是语义/契约常量，非回归量，值由纯函数形态决定）；**且只管抽签（账一-a）——冷 A* 重算（账一-b）由 §3.0 接法红线拦，不进本阈值。**
- **兜底**：若 RNG 常规 draws 实测 > 0.045ms（L1 满属性有额外 draws），混沌余量相应收缩——红线的**真实约束是 `RNG_TICK_LIMIT_MS=0.10` 总行**，`CHAOS_TICK_LIMIT_MS` 只是把「混沌分额」显式化，**不放开总行**。建议 bench 侧同时断言 `RNG+混沌 ≤ 0.10`（一次断言管总行），`CHAOS_TICK_LIMIT_MS` 供施工单按频率快速校验。

### 3.2 建议：新增代码契约常量（非红线，随接线施工对齐）
```
# chaos.py 已落 chaotic()/chaotic_at()；接线施工需订：
CHAOS_EMOTION_REGRESS_INTERVAL_TICKS = 60   # 情绪回落区间（慢变量，禁每 tick）
```
- 与 `_PERCEPTION_EVERY_N_TICKS` / `FAST_FORWARD_TICKS_PER_FRAME` 同族（**代码契约常量，非 bench 红线**）。
- 定区间使情绪回落落在 0.008ms/tick 档（§2.3）。

### 3.3 不新增行（并入既有）
- **不单设** `CHAOTIC_PER_CALL_LIMIT`——单次 `chaotic()` 的 9.3µs 是语义决定的常量，卡它无意义、只会假红。
- **不触碰** `RNG_1M_DRAWS_LIMIT_MS`（聚合警戒线，混沌非其中心）。
- **thresholds.py 本单零改动**（红线为提案，待裁后施工单落地）。

## 4. 守卫点 / 语义约束（接线施工须守住，防红线「达标但语义错」）
- **T2 回放逐位一致**（C5）：`chaotic_at(stream, rng, tick)` 同流同刻恒同值、与调用序无关——消费点不得引入「抽签推进进度」或「调用序依赖」。
- **出戏边界（裁 14-5 延续）**：混沌返回值只被内核消费；熵值/seed/tick/luck **不进 prompt、不进感知帧、不进协议三面**。预算只测内核成本，不测戏外展现。
- **禁「每 tick 每 NPC」热循环**：m5-plan 明示「混沌每 tick 抽样不得进热循环」。若情绪回落/寻路扰动实现里逐 NPC 逐 tick 抽样，即使单次 9.3µs，50 NPC 即 0.465ms/tick（9.3x 上界），属**实现回归**而非语义所需。
- **向量化批量缓存边界**：若为省 PCG64 重建而把某区间内的 50 个抽签**一次 `gen.random(size=50)`** 算好缓存（键 = `(材料, 区间起始 tick)`），仍满足逐位一致（键内确定性）。实测 `gen.random(size=50)` ≈ **0.6µs**（vs 50×`chaotic_at()` ≈ **497µs**，**~830x**）——但**缓存生命周期/失效必须以「材料」为键**（inject 重播种后旧缓存必须作废，否则存的是旧混沌）。

## 5. 待裁 / 交叉
1. **消费点抽样频率**：寻路（事件驱动）、情绪回落（区间 N=60？）——需 Claude/架构域接线时定；pi 只给成本表（§2.2/§2.3 三档）。
2. **红线命名**：`CHAOS_TICK_LIMIT_MS` / `CHAOS_EMOTION_REGRESS_INTERVAL_TICKS` 为**提案名**，随落地实现名对齐（对齐 M4-P1 §4.1 先例）。
3. **对 opencode M5-A2 量级结论：采纳主体 + 修正适用范围**。
   - **采纳**：事件量级（20–150 条/游戏日、密度 0.0002–0.002 条/tick）、存储（~60KB/游戏日）、
     「**事件面**不需按帧摊还封顶」、「不新增 EventKind / 不新增表 / 抽样不落事件」全部成立——
