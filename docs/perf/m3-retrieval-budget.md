## 1. 两段预算切分
M3 检索链（vec-preplan §18 硬边界不变：**向量只影响候选集，打分链一字不动**）：
```
retrieve(store, query, scorers=)
  ├─ 候选生成（M3 新增，A4 接 VectorIndex）：vec k-NN / numpy 余弦 → k=20 候选
  └─ 打分链（M2 现有）：base_score × Π(Scorer) → sort → top_k=8
```
### 1.1 候选生成（实测，d=384）
| 方案 | 单 NPC（n=600 可见） | 说明 |
|---|---|---|
| B numpy 余弦（降级兜底） | **0.019ms** | normalize 在外层缓存（写入时算），检索只做一次 matvec + argsort[:8] |
| A sqlite-vec（主） | 未实测（依赖扩展，opencode A3 落地后补）——vec-preplan §3 估「量级同亚毫秒」 | SQL 内 ANN；B 的 0.019ms 给 A 的是**同量级上界参考** |
| 全库 3 万条（最坏：过滤失效退化） | 1.00ms | vec-preplan §6 V6 红线（治理过滤 JOIN）失效时的退化量级 |

### 1.2 打分链（实测，M2 现有 `retrieve`）
| 候选 n | ×0 钩子 | ×2 钩子（confirmation+mood） | 每钩子净增 |
|---|---|---|---|
| 600（= 可见条目量级） | 0.509ms | **0.862ms** | +0.177 |
| 1000（= 每 NPC 满） | — | — | 线性外推 ~1.4ms |
| 3000（= 5  NPC 混入退化） | 3.06ms | **4.91ms** | +0.92 |
| 30000（= 全库，红线失效退化） | 37.1ms | **57.8ms** | +10.3 |

**切分口径**：M3 单次检索 = 候选生成（0.02）+ 打分（top_k=8 前的**候选内**打分）。
关键结构性事实：**M3 候选生成产出 k=20，打分链只打 20 条**（不是全量）——
所以 §1.2 表里 n=600 的 0.862ms 是「**候选集未收缩**」的退化口径；M3 正常形态是
候选 20 条 → 打分 ≈ 0.029ms（按 0.862/600×20 线性外推）+ 2 钩子。
→ **M3 正常单次检索 ≈ 0.02（候选）+ 0.03（打分 20 条）= ~0.05ms/NPC**；
n=600/3000 全量打分是「向量候选缝断链 / JOI失败退化」的**哨兵口径**，红线要按退化口径给。

> **⚠ 模型低估修正（M3-P2 实测回填，2026-09-24，pi 实测 → Claude 落档）**：
> 上式按纯 numpy 参考实现估 ~0.05ms/NPC，但 M3-P2 用 **A4 治理 JOIN 同语义参考实现**
> 实测（test_bench_retrieval.py，本机暖态中位）：候选 0.233ms + 打分 0.057ms ≈
> **0.29ms/NPC**——低估 **6~52x**（IN-JOIN 80 参 + 4x 过取 + dict 组装成本，纯向量
> 运算建模罩不住）。**红线值不变**（0.30/0.30/2.00/12.0 本就是按退化口径给的），
> 但「50 NPC = 2.5ms」的旧估算作废：常态口径按 50×0.29 ≈ **14.5ms** 逼近 tick 预算
> ——结论反而更强：**检索触发必须决策/prompt 驱动**（防呆红线），sqlite-vec 真实现
> 后复核对账（预期 IN-JOIN 成本下降）。

## 2. 防呆红线（延续母本 `m2-p4` §3.3 + talking.txt 活跃约定）
**检索触发必须保持决策/prompt 驱动**（DESIGN §8：L2 LLM 决策装 prompt 时才检索；
L1 断线兜底低频；零触发 = 每 tick 零检索成本）。
**反证数据（本机实测，为什么要盯）**：
| 场景 | 600 候选 | 3000 候选 | 判定 |
|---|---|---|---|
| 每 tick 全量检索 50 NPC（含 2 钩子） | **43.1ms/tick** | **245.5ms/tick** | 破 16.6ms **2.6x / 14.8x** |
| 每 tick 广播（只候选生成，不打分） | ~1ms/tick | ~9.3ms/tick | 600 候选勉强、3000 破线 |
| 按需（决策驱动，假设 ≤10 次/tick） | ≤0.5ms/tick | ≤0.5ms/tick | ✅ 常态 |
→ **M3 接线若把检索挂进 tick 固定序，无论打不打分都破线**（600 候选含打分量 2.6x）。
正确形态：`retrieve` 仍只在**装 prompt / 断线兜底**时被调，候选源从 `iter_visible`
换成 `VectorIndex.knn`（vec-preplan §18）——**调用点不变，只换候选生成器**。

## 3. V5 裁决输入（召回时机：每 tick / 按需 / 批量窗口）
| 方案 | 50 NPC 成本（本机实测） | 实时性 | 判定 |
|---|---|---|---|
| **按需**（决策/prompt 驱动，单 NPC 0.019ms 候选 + 20 条打分） | 触发时才付：9.1ms/窗口（若 50 个同时触发） | 最高（每次决策取最新） | **推荐**（延续 M2 频次红线，零新风险） |
| 批量窗口（每 N tick 全体重算一次，摊销） | 一次全量 = 2.65ms（n=600，含 matmul + top8）→ 每 N tick 摊销 2.65/N | 窗口内旧候选（N tick 前算的） | 可选：仅当 M3 行为链确需「每 tick 都有候选可读」时；N≥2 即摊销 ≤1.33ms |
| 每 tick 广播 | 609ms/tick（0.019×50 + 43.1 打分若含）～至少 9.4ms/tick（只候选） | 最高但最贵 | **不推荐**：见 §2 反证 |
**pi 建议（V5）**：**按需为主 + 批量窗口可选**。理由：① 检索只在装 prompt 前发生（DESIGN §8 决策链），按需=零常态成本；② 批量窗口的唯一收益是「候选可缓存复用」，但 M2 的 `Scorer` 打分依赖 query（context/mood），候选与 query 弱相关——窗口缓存收益小、复杂度高；③ 每 tick 广播已用数据否掉。
**注意（矩阵乘法反直觉）**：50 NPC **批量矩阵**（Qhat@Mhat.T）反而比 50 次**串行 matvec**慢（2.65ms vs 0.91ms @n=600）——小 n 下 BLAS 批处理开销 > 收益。若 opencode A3/A4 想用批量路径优化，须先用 bench 证伪再上（红线按串行口径给）。

## 5. 附录（M3-P3，2026-09-25）：C3 chunk 失效通路实测 + 提案待裁
> 本件任务书从「检索缝预算」扩到「C3 失效通路纳入观察」——按惯例新热路径要有数。
> 本文档已定为 M3 检索域的实测归档处，故失效实测数据收录在此（§1-§4 只读不动）。

### 5.1 通路与口径
C3 收编 main `5724aa7` 的两段（`sim/world/pathfinding.py` + `sim/world/map.py`）：
1. **事件扫描**（`event_tile_position` 纯函数）：每 tick 对**全事件流**遍历一遍，
   TILE_CHANGED 全量取坐标，MATTER_* 仅 `x/y≥0`（-1 未定位哨兵不标脏，C4 域约束），
   无关 kind → `None`。成本 ∝ **事件总数**（与坐标落点无关）。
2. **失效本体**（`Pathfinder.observe_events` 标脏 → `TileMap.drain_dirty` →
   `PathCache.invalidate` 逐 chunk 精确剔除非途经条目）。成本 ∝ **缓存条数 × 脏 chunk 数**
   （`invalidate` 每个脏 chunk 全表扫一遍缓存；精确失效非全清）。

口径与 §1-§4 同源：暖态中位（`warmup_rounds=1` + median）、固定seed、48×48=9 chunk 全通开阔图
（无遮挡 → 路径长度/扫描成本取同条件最坏）。失效本体是**消费式**（标脏即 drain、剔除即删），
bench 每轮用 `setup` 复原缓存快照，计时窗口只含失效通路（不含 A* 回填：单条 ~0.65ms，属寻路本身）。

### 5.2 实测数据（本机暖态中位，`sim/tests/bench/test_bench_chunk_invalidation.py`）
| 场景 | 实测 | 占 tick 预算 16.6ms |
|---|---|---|
| `event_tile_position` × 50 定位事件 | **0.007ms** | 0.04% |
| `event_tile_position` × 200 混合（150 无关 MOVE + 50 定位） | **0.036ms** | 0.2% |
| `event_tile_position` × 1000 无关事件 | 0.054ms | 0.3% |
| `event_tile_position` × 5000 无关事件 | 0.267ms | 1.6% |
| **失效本体** 100 路径 × 50 定位事件（≈9 脏 chunk） | **0.076ms** | 0.5% |
| 失效本体 500 路径 × 50 定位事件 | 0.192ms | 1.2% |
| 失效本体 1000 路径 × 50 定位事件 | 0.320ms | 1.9% |
| **失效本体 4096 缓存（max_entries 打满）× 50 定位事件** | **1.18ms** | 7.1% |
| 失效本体 100 路径 × 25 定位+25 未定位（脏 chunk 减半） | 0.056ms | 0.3% |
| 失效本体 4096 缓存 × 全 9 chunk 脏（退化哨兵） | 1.04ms | 6.3% |

**成本模型验证**：脏 chunk 数 1→9，4096 缓存下 0.14→1.11ms（近似线性，验证「缓存条数 × 脏 chunk 数」）；
缓存 100→4096（50 定位）：0.076→1.18ms（近似线性）。半定位混合批成本降 26%（脏 chunk 9→5）。

### 5.4 观察项（不设红线，留预审核）
- **大图全脏风险**：128×128=64 chunk 全脏实测 ~10ms = tick 预算 **60%**。当前无形态触发
  （定位事件稳态 ~20/tick、p99 50；48×48 只有 9 chunk）。若 M4 起出现「全图重绘 / 批量建造 /
  地图尺扩大」形态 → 按 `test_chunk_invalidation_full_dirty_degraded_probe` 档位复核，
  届时再裁是否设红线（备选优化：`PathCache` 按 chunk 倒排索引，避免逐 chunk 全表扫）。
- **未定位哨兵语义**：x/y=-1 不标脏是 C4 域约束（避免把整图当脏）—— bench 实测其收益
  （成本降 26%）可作该约束的性能佐证，不是放宽理由。
