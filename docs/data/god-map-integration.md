# GOD 地图素材利用方案（整图替换可行性专项 · 2026-10-12 实测核验）

> 上游：`docs/data/god-reuse-final.md`（素材四档定稿，D1-D5 已裁决兑现——17 张古风角色已入库）。
> 本文回答下一个问题：**地图素材怎么用**。此前「整图不引入」的初判被本轮实测推翻一半，
> 关键证据与修订理由见 §1。核验日期 2026-10-12，全部结论基于本地文件实测。

---

## 1. 关键实测发现（推翻初判的两件事）

**发现一：GOD tileset 不是模块化瓦片库，是整图切片。**
桃花源与空城计的 `tiled-map.json` 实测引用瓦片数均为 **14000/14000 全量**——`tileset-0.png`
（4480×3200，140 列×100 行 @32px）是把整张 AI 渲染图**按网格直接切开**的产物，每块碎片
在原画中只出现一次。推论：

- ❌ **「摘瓦片拼进临河镇」路径不可行**——碎片按原画连续性切分，抽出来拼 96×96 的
  语义布局会全是接缝（建筑大面尤其不可能）；只有恰好在单格内自含完整的小物件
  （独立树/灯笼/石块）可摘，收益极小
- ✅ **「整图替换」是地图素材的唯一高价值用法**——视觉收益是一张完整无缝的古风图

**发现二：整图替换的三大配套，GOD 已经备好。**

| 配套 | 实测 | 价值 |
|---|---|---|
| 碰撞层 | `Collisions` tilelayer（140×100）现成 | 直接转临河镇 collision 布尔层，**不用自己画不可走区域** |
| 地标锚点 | `map_pack.json` 10 个 location 带坐标（祠堂/染坊市集/梯田/溪桥/书塾/祖屋/客栈院落/村广场/牌坊山门/档案室） | 差事地标/片区锚点重映射的**现成语义选点库** |
| 渲染分层 | 17 层（地面×2/装饰×2/墙/室内/前景×2/碰撞/交互/出生等） | 前景层提供「树冠/屋檐在人前」的纵深——临河镇单层格式没有的观感 |

**动机补强**：17 张古风角色已入库（`aeedf0e`），**现在的 Zelda-like 西幻底图反而成了风格异类**——换古风底图是完成风格统一，不是锦上添花。

## 2. 三条路径裁定

| 路径 | 评估 | 结论 |
|---|---|---|
| A. 摘瓦片混用 | 被「整图切片」事实否定（§1 发现一） | ❌ 仅保留「小物件点缀」的残值，不作为目标 |
| **B. 整图替换底图** | 视觉/语义配套全齐；代价集中在 sim 侧坐标重映射（§3） | ✅ **推荐** |
| C. 双地图并存 | 单地图架构上加多图加载是新架构面；临河镇语义没有迁移需求 | ❌ 过度设计 |

## 3. 方案 B 施工分解（整图替换：桃花源为底图）

### 3.1 选图

**推荐桃花源**（taohuayuan-online）：村落题材与临河镇社会构成（药铺/农田/集市/住宅）
直接对位；空城计是军事城池，军事元素与临河镇无对应玩法。
已知瑕疵：预览图右上角有太阳能板/信号塔（AI 生成的时代错位，此前美术评估已指出）——
处理见 §4 D9。

### 3.2 地图转换器（新 content 管线件，build_god_town.py）

```
输入：assets/god-packs/taohuayuan-online/{tiled-map.json, assets/tileset-0.png}
处理：
  1. tileset 整图缩半 32px→16px（4480×3200→2240×1600，网格数不变仅像素密度减半
     ——D1 甲既定路线，零工具依赖同 build_god_characters.py 手法）
  2. 渲染层压合 → 临河镇内部格式 ground 单层：
     Bottom Ground / Exterior Ground / Wall / Exterior Decoration 逐格叠合取最上非零
  3. Collisions 层 → collision 布尔层（1:1 直转）
  4. （若 D7 选装饰层扩展）Foreground L1/L2 → 新增可选 decor 层
输出：sim/content/linhe-town.json（内部格式，TileMap.from_json_file 直接可加载）
      + client/public/assets/tilesets/god-town-16.png（缩半 tileset，入库）
```

尺寸影响：140×100（=70 chunks，现 36）比 96×96 大 52%，同 16px 下前端画布
2240×1600 与现 1536×1536 同级，渲染性能无虞。

### 3.3 sim 侧坐标重映射（真正的工程量所在）

硬耦合面盘点（全部与 96×96 布局绑定，换图必须重映射）：

| 耦合点 | 现状 | 重映射方案 |
|---|---|---|
| 五区锚点 `HOME_BASES` | (28,42)/(14,68)/(82,38)/(46,86)/(78,75) | 从桃花源 10 地标中选 5 个做片区核（如村广场/染坊市集/梯田/祖屋/溪桥），锚点取其 anchor_tile 附近可走格 |
| 50 人定籍表 | sha256 确定性分配（重跑算法即得新表，需落新常量） | 算法不变，重生成后硬编 |
| 片区站点（eat/rest/work） | 与 build_town.py 布局同源的硬编码 | 按新五区在「语义对位地标」附近选点 |
| 药铺（主角家） | (12,16)-(20,22)，门 (16,22) | 桃花源祖屋/客栈院落对位；陈默身份叙事（药铺学徒）随图微调或选点就药铺位 |
| 出生点 SPAWN | (16,32) | 村广场 anchor 附近开阔可走格 |
| 20 个差事地标 | 按旧地标硬编码 | **直接用 map_pack.json 的 anchor_tile**（10 地标语义现成，差事目标重指到新锚点） |
| 测试面 | test_m7_town_map / errand / territory / believable 等坐标断言 | 全面重写（最大单笔工作量） |

### 3.4 风格统一收益

古风底图 + 17 张古风村民 + 古风角色重切 16×32（已入库）= **全画面风格首次统一**；
Zelda-like 西幻瓦片从运行时退役（调色板管线与原件区保留——历史重建与回放仍可用）。

### 3.5 风险与前置验证

1. **切片对齐风险**：AI 渲染图的 32px 切片可能有半像素错位，缩半后 16px 更敏感
   ——动工前先做「重组可视化抽查」（临时 HTML/Tiled 打开转换结果，肉眼查接缝），
   不合格则该图不可用，止损在第一步
2. **压平纵深损失**：前景层压平后人会「站在树冠上」；若观感不可接受走 D7 装饰层扩展
3. **协议面**：前端 BootScene 静态加载地图（实测确认），**换图不触 WS 协议**——
   `gen:protocol --check` EXIT 0 仍是硬验收
4. **确定性红线**：转换器必须无随机/无时间依赖，重跑逐字节一致（C5，同现有管线纪律）

## 5. 施工顺序（若 D6-D10 全按建议裁）

```
1. 重组可视化抽查（半天级，不合格即整体止损）
2. build_god_town.py 转换器（tileset 缩半 + 层压合 + collision 直转）+ 确定性测试
3. 前端换静态资源（BootScene 指向新图，零协议面）
4. sim 坐标重映射（五区锚点/定籍表/站点/药铺/出生/差事地标）
5. 测试面重写 + 全量门禁（含 gen:protocol EXIT 0 零漂移断言）
6. 实况验收：村民在古风图上按作息走动、差事往返、念头注入闭环
```

**量级判断**：步骤 2-3 是管线活（1-2 天级）；步骤 4-5 是本单主体（坐标+测试重写，
数天级）；整体是「M6 尾巴 + 美术统一」的一张中大型施工单，不动架构、不触协议、
不破 C1-C6。
