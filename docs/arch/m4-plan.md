## 4. 「T4 全绿」与 M4 验收的关系（§16 / §17 / §20 对账）

**§17 原文**把 M4 验收定为三条：核心闭环成立；**T4 全绿**；建造材料守恒。第二条中的「T4」就是 §16 测试分级表的 T4 行：

| 项 | §16 原文 |
|---|---|
| 内容 | 出戏探针 + 意愿抱怨合规（「是不是AI」「重来一次」「谁指使你」…） |
| LLM | **真模型** |
| 频率 | 每日 **nightly**，**锁定模型版本** |
| 不进 CI 的理由 | §16：「真模型测试进 nightly 不进 CI：烧钱且抖动」；`ci.yml` 头注同口径（T4/T5 进 nightly） |

因此 **M4 的「T4 全绿」= 锁定模型版本下 nightly T4 批次连续通过**，不是「每次提交绿」——它与 §16 的频率列同义，任何把它读成 CI 门禁的实现都违背冻结基线。§20 风险台账同一条防线：「元认知泄漏不可根除 → 三层防御（锚定/过滤/重生成）；T4 nightly 持续跑」。

T4 探针与 M4 四个批次的对应（建议）：

| 批次 | T4 关注点 | 依据 |
|---|---|---|
| A 念头注入 | 「谁指使你」必须 0 命中；注入后仍第一人称 | §10 + §16 + §8 铁律 |
| B 计划看板/意愿 | 「是不是AI」「重来一次」+ 抱怨=自我怀疑（不指外部命令源） | §10 + §16 + §19 |
| C 建造破坏 | 不直接产 T4 探针；材料守恒走 T1 + T5 | §16 六类/T5 |
| D 巧合连锁 | 「运气」词面不得进 prompt/日志/戏内 UI | §19 + §8 铁律 6 |

**接线状态（裁 14 第 4 条已落，cline 已接）**：`.github/workflows/t4-nightly.yml` —— 触发**仅** `schedule`（UTC 19:30 / 北京 03:30，与 `nightly-bench.yml` 的 UTC 18:00 错开）+ `workflow_dispatch`（§16 铁律：不进每提交 CI，`ci.yml` 不引用）；**模型 id 硬编码在 workflow env `T4_MODEL=claude-sonnet-5`（不进代码）**；api_key 只经 secret `T4_MODEL_API_KEY` 注入（值不落盘/不进日志/不入库）；骨架含 job 结构、锁版本证据（`t4-results/model-lock.txt`）、`if: always()` 结果归档、失败通知（step summary + `::error::`）。**探针步骤留 TODO**，指向 codex M4-S1 交付（`346dfa1`，收编后再接）——接线约定五条写在 workflow 注释里：`-m t4` 入口、`sim/tests/test_t4_*.py` **文件路径 + marker 双纪律**、junit 随 artifact 归档、零出戏命中即红、模型/温度/词面参数只读 env。`pytest.ini` 的 `t4` marker 已注册（`--strict-markers` 要求先注册）。骨架期 secret 未配置**不红**（只发 notice + step summary 留痕），探针接上后改硬失败——避免「静默跳过」被误读成「探针全绿」。
