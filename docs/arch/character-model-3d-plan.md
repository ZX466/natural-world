本次只读 PNG 文件头及大小，19 张合计 **42,880 bytes，约 41.88 KiB**；这是磁盘文件总量，不是 GPU 占用或实际 HTTP 开销。已有图可继续做回退，保留它们不会成为新增模型包体的主要来源。

Sprite 始终面向相机，因此四向贴图能提示朝向，却不能提供绕人物观察时连续变化的体积；把走环改快也不会生成跑步、起跳或落地姿势。[Three.js Sprite 文档](https://threejs.org/docs/pages/Sprite.html) 当前多出的贴图行不代表渲染器已支持独立动作，现入口仍是 `walkFrameFor` 的走环/站立帧。

## 2. 分档与工期

以下是本方案的工程估算，**不是报价或已承诺排期**。1 人日约为 1 人的 1 个完整工作日；总量包含基础测试、Phaser 回退检查与一轮美术修改，不含等待用户审稿、寻找供应商、采购、任务 1–4 的实现及新玩法。B–D 都从本轮动作交付后的同一基线计算，不能相加。

| 档位                        | 交付范围                                                                                                                                | 工程 / 美术人日  | 合计与约需日历工作日                               | 主要代价                                                        |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ---------------- | -------------------------------------------------- | --------------------------------------------------------------- |
| **A：保留 billboard**       | 待本轮任务 1–4 交付后沿用朝向、走跑、步频、跳跃成果；不新增模型                                                                         | 新增 3D 为 0 / 0 | 0                                                  | 仍有纸片感；没有真正的身体、衣袖与关节动作                      |
| **B：方块人物试点（建议）** | 主角 + 1 种村民外观；共用方块关节层级，以节点旋转做动作；其余人和动物保留 billboard。用 50 人复用试点模型测负载，不冒充已做齐 17 种外观 | 5–8 / 3–5        | **8–13 人日**；工程、美术各 1 人约 **7–10 工作日** | 方块风格可能损失古风服装细节；混合人群需用户接受                |
| **C：完整方块外观池**       | 覆盖 `protagonist`、通用兜底及 17 个 GOD 外观键；共享动作层级，逐个检查衣着/轮廓，不要求 19 套独立网格                                  | 8–13 / 12–22     | **20–35 人日**；两人约 **15–25 工作日**            | 美术量明显增大；只换颜色不足以保留 17 种辨识度                  |
| **D：低面数骨骼模型**       | 主角 + 通用兜底 + 17 种外观，共享人形骨架；glTF/GLB、蒙皮、动作混合与逐外观验收                                                         | 12–20 / 20–40    | **32–60 人日**；两人约 **25–40 工作日**            | 需要建模、UV/贴图、绑骨、权重、动作制作；不同来源骨架不保证兼容 |

B 的工程量分解：模型/共享姿态适配 2–3 日，头顶锚点/遮挡/资源生命周期 1–2 日，回归与负载验证 2–3 日。美术 3–5 日包括主角与一个村民的比例、服装轮廓和基础动作。C 剩余外观按每种约 0.5–1 日制作及回看估算；复杂衣装需上调。D 假设共用骨架、基础衣装变体和有限动作集；逐人独立体型、脸部动画、布料模拟与写实风格均不在估算内。

建议的最低动作集为站立、走、跑、起跳、空中、落地；当前其他行为可以先退回站立表现，单独登记缺口，不把它们算作已有完整动作。素材采购与委托费用暂不填金额：选中来源后按“工程人日 × 日成本 + 美术人日 × 日成本 + 素材授权/委托费”核算，模型格式通用不等于素材免费。

**A 的持续代价**：旋转视角仍是四向切换，放大时像素与纸片轮廓明显；更丰富动作和服装仍需逐方向逐帧绘制。八向图或由 3D 离线烘图可以改善方向过渡，但仍是 billboard，不能作为“真 3D 替换”的验收。A 也保留了现有辨识度与最小资源负担；共享运动层的投入以后可以继续复用，不必为换模型重做移动逻辑。

## 3. 素材管线怎样增量扩展

### 3.1 保留现有产物与来源

- 地形链：`terrain_class.classify` → `build_god_town.derive_terrain` → 地图/高度产物；`build_block_atlas` 读取地图、地形图与高度表，生成方块图集。

- 现有 CC0 / Apache-2.0 登记、17 张选片范围、修改说明及 [THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md) 原样保留。新 3D 人物不能靠改扩展名或四向 PNG 自动获得完整体积、拓扑与骨架；如果以原图作衍生参考，需另记制作人、参考来源及修改情况。

未来可另设 `sim/content/assets/characters-3d/` 源区与 `client/public/assets/models/characters/` 运行时产物区，**此处只是建议路径，本轮未创建**。B/C 可用固定方块部件、枢轴与配色描述构建模型；D 保留可编辑源文件，导出 glTF 2.0 的 GLB。清单记录逻辑外观键、产物哈希、缩放/脚底/头顶锚点、骨架版本、动作名及对应旧 PNG；未知键、缺模型或校验失败时退回原图。

D 的源模型、纹理、动作必须分别登记作者、精确来源版本、许可及再分发条件，核对后才纳入产物。现有素材登记只说明当前 PNG 的来源，不代表新模型或第三方动作已经获准使用。原件缺失的构建不得伪报成功；运行时产物需要可从明确版本的源重建。

**模型只是最终姿态的消费者。** 任务 1–4 尚在实施，不能预写成已有 `surfaceHeight`、跳跃相位或某个新 Actor 字段。未来接入前要核对其真实类型，再确定模型适配需要的逻辑位置、脚底高度、支撑面、朝向与动作进度；确需补充呈现信息时，也应在共享层统一定义。

1. 位移与跳跃由现有权威状态及最终共享回放层决定；模型动画保持原地动作，根节点不得再次累加动画根位移。起跳/落地按同一回放时刻取样，不能把收到包的墙钟当作脚离地的瞬间。
2. 走/跑步相与**实际呈现位移**同源；暂停、1×/4×/16×、切速、重连与加载需要与 billboard 相同的复位语义，不能简单对 mixer 再乘一次全局倍率。姿势只影响显示，不增加事件、协议字段或 `state_hash` 内容。
3. 模型根朝向使用世界方向；billboard 继续做相机相对行选择。相机转动不能让实体跟着转身。脚底锚点贴最终支撑面，腾空时人体与地面影子分开；名字/气泡改用模型头顶锚点，不能沿用 Sprite 的高度计算。
4. 当前 `GreaterDepth` 主角 Sprite 轮廓不能原封不动套到多部件/蒙皮模型；试点必须验证等价遮挡提示，且不得让不可见 NPC、姓名或气泡穿墙显露。模型不参与服务端碰撞，也不改变移动拾取与编辑拾取的分离。

D 的 GLTFLoader、SkeletonUtils 已属于 Three 的 add-on；当前锁定版本是 `0.180.0`（[package-lock.json](../../client/package-lock.json)），不因建模提案升级引擎。独立人物需正确复制骨骼及维护动作状态；共享几何/材质的所有权与每实例 mixer 要分别释放，不能删除一个 NPC 就销毁全池资源。[GLTFLoader 官方说明](https://threejs.org/docs/pages/GLTFLoader.html)、[SkeletonUtils.clone](https://threejs.org/docs/pages/module-SkeletonUtils.html)、[AnimationMixer](https://threejs.org/docs/pages/AnimationMixer.html)；版本依据为 [r180 Loader](https://github.com/mrdoob/three.js/blob/r180/examples/jsm/loaders/GLTFLoader.js) 与 [r180 SkeletonUtils](https://github.com/mrdoob/three.js/blob/r180/examples/jsm/utils/SkeletonUtils.js)。

## 6. 试点门槛、风险与止损

以下均为**将来实施时的建议验收项，不是本次已通过的读数**。B–D 开工前先确定参考设备/视口和可接受画风；工期内保留一轮修改，后续换风格需重估。

| 关口         | 通过条件                                                                                                                          | 不通过时                                                              |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| 美术样例     | 主角 + 1 NPC 的正/侧/背与 360° 转镜可看，服装/比例符合用户选定方向；用户明确选择保留样例                                          | 保留 A，停止扩大 17 人池；不把技术通过当作画风认可                    |
| 姿态与同源性 | 对比两种人物呈现的根位置、朝向与脚底高度；走/跑/停、1×/4×/16×、切速、暂停、h1→h2/h3→落地、断线/读档场景不漂移；落地仍由服务端确认 | 修正共享姿态适配，禁止另造模型本地落点或重复根位移                    |
| 视觉语义     | 姓名、气泡、同格偏移、主角遮挡提示正常；不可见 NPC 不出现；旧动物保持原形，未知/损坏模型能退回 PNG；Phaser 同一存档继续可玩       | 关闭模型分支回到 billboard，不删旧资产                                |

glTF 使用右手坐标、Y 向上、线性单位为米；本项目的格子单位通过导出/加载适配固定换算，不据此改成另一套模拟坐标。[Khronos glTF 2.0 规范 §3.4](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units) 衣袖穿模、脚底滑步、材质受昼夜影响不一致、姿态包体增加和 17 外观辨识度下降，均须在样例关口暴露；不能留到全部替换之后才检查。
